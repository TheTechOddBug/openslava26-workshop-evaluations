The problem

"It looks good" is not an evaluation

You wire a model into your app, try a few questions, read the answers, and decide it works. Then you change the prompt. Did it get better?

  • You can't tell whether the model improved between versions.
  • You can't tell whether a prompt change helped or hurt.
  • You don't see the regressions on inputs you didn't try.

"Spend time establishing success criteria first."

Anthropic documentation, on building evaluations

~3 min. Ask the room: "How do you know your last prompt change was an improvement?" Most people will say they looked at a few outputs.

The point: evaluation comes before improvement. Without it, prompt work is guessing.

The fix

An evaluation is a function that returns a number

score = evaluate(case, response) → 0.0 … 1.0

Track it

The same cases every run. Watch the number move across model versions and prompt changes.

Compare it

Two models, two prompts, side by side on identical inputs. The difference is the effect of your change.

Gate on it

Put a threshold in CI. A drop below it blocks the release, like a failing unit test.

~2 min. Keep this short. Everything in the workshop is a different way of writing that one function, from a string comparison to a second model acting as a grader.

~3 min. The rule of thumb: use the cheapest mechanism that fits the shape of the task. Classification gets exact match, code gets tests, open-ended text gets a judge, and the judge gets checked.

Would you trust 100% on 5 cases? On 50?

Exact match normalises case and trailing punctuation, then checks whether the reference is contained in the response. The lab text suggests extra words cause failures. In practice, failures mean a wrong label, or an answer that mentions two labels.

Llama 3.2 3B tends to answer "I would classify this as positive." It still passes, which is a good prompt to discuss how lenient a grader should be.

Concept · Lab 02

Before you buy a bigger model, fix the prompt

85%

Claude Haiku with a minimal prompt, on a complaint classification task

100%

The same Haiku model, with category definitions and nine few-shot examples

From Anthropic's prompt evaluation course, cited in the Lab 02 notes.

A refined prompt adds

  • The exact labels allowed, with a definition for each
  • A few worked examples, including edge cases
  • A strict output format: "exactly one word"
  • A rule for ambiguous input: "if mixed, answer neutral"

Prompt work is a one-time cost. A larger model is a cost on every call.

~3 min. Set up the experiment: hold the model fixed, change only the prompt. Any score difference is the prompt's effect.

Concept · Lab 03

Overlap metrics count words, not meaning

Source: "The merger was approved by regulators after six months of review."

SummaryMeaningROUGE-LA judge would say
A · "Regulators approved the merger following a six-month review period."correcthighgood
B · "The merger received approval after a lengthy regulatory review."correctlowergood
C · "The merger was rejected by regulators after six months."wrongmoderatebad

ROUGE-L ranks A > C > B and puts the wrong answer above a correct paraphrase. BLEU measures n-gram precision, ROUGE-L longest-common-subsequence recall, fuzzy match character edits.

~3 min. These metrics are still useful as a cheap first signal: below 0.2 ROUGE-L, a summary is probably missing content. Just don't read them as quality.

Concept · Lab 04

The grader for code is code

code_exec

Extract the code from the answer (fences, <think> tags and prose are handled), append the case's tests, run it in a subprocess. Exit code 0 means 1.0.

sql_exec

Run the model's query and the reference query on an in-memory SQLite database. Compare result sets: ordered if the reference has ORDER BY, any order otherwise.

numeric

Take the final number in the answer and compare it with the reference within 1%. Arithmetic is graded by arithmetic.

A loop or a list comprehension, a join or a subquery: the grader doesn't care how the answer is written, only whether it works.

~2 min. Deterministic and functional. If you can write the acceptance criteria as tests, do that before reaching for a judge.

Good moment to compare a coder model with a general small model on the same cases. Qwen3's think block is stripped before the code runs. If its answer is cut off, raise Max tokens.

Expect code-101 to fail for every local model. Say it in the room so nobody thinks their setup is broken. Qwen2.5 Coder 7B skips the "ignore lines without =" rule (ValueError: not enough values to unpack), Llama 3.2 3B drops a value that contains = (KeyError: 'TOKEN'). Use it for "would you have passed this by reading it?". For passes, point people at code-102, code-103 and code-105 with the coder model.

A NameError saying merge_env_files is not defined means Qwen3 4B used its whole token budget thinking and returned no code.

sql-101 also fails for every local model. The answer needs one row per category (2 rows). Qwen2.5 Coder 7B adds LIMIT 1 and returns only the top row overall (rows_candidate=1 rows_reference=2); Llama 3.2 3B groups by category only and mixes the models' averages. Good prompt for "the detail string tells you what kind of mistake it was". "No SQL query found in the response" means Qwen3 ran out of tokens.

Concept · Lab 05

A judge scores five dimensions, 0–10 each

CorrectnessIs the answer actually right?
CompletenessDoes it cover every part of the question?
RobustnessEdge cases, ambiguity, unusual input
ClarityEasy to read and follow?
EfficiencyConcise, economical approach?
  • Combined into one weighted score in [0, 1]. Weights differ by category: code leans on correctness and robustness.
  • With a reference answer the judge has an anchor and scores more consistently.
  • Use a different model as judge than as candidate.
  • Avoid reasoning models as judges. They can spend the whole budget thinking and return no score.

~3 min. The judge is itself a language model: inconsistent, swayed by style, sometimes wrong. That is the bridge to Lab 06.

Concept · Lab 06

Who judges the judge?

Score the same answers with the judge under test and with a stronger reference judge, then measure agreement.

Pearson rLinear agreement on scores
Spearman ρAgreement on ranking only
Rank agreementShare of pairs ordered the same way
MAEAverage gap, in points out of 10

Verdict

reliable r ≥ 0.7 and MAE ≤ 1.5 questionable r ≥ 0.4 unreliable otherwise

Known biases

  • Self-preference: a model rates answers in its own style higher.
  • Position: in A/B comparisons, the judge favours one slot regardless of content.

~3 min. The chain ends with humans: to validate the reference judge you need human labels. This view automates the step below that.

The lab text calls the middle verdict "uncertain"; the app shows "questionable".

From workshop to production

Make the matrix a release gate

  1. Keep a fixed evaluation set: the same cases every run.
  2. Set a threshold per mechanism: exact match ≥ 0.90, judge ≥ 0.75.
  3. Run the matrix on every model, prompt or temperature change.
  4. Block the release when any score falls below its threshold.

The dataset and thresholds are the specification. If you can't write them down, you can't automate the gate.

In the app: the Matrix's Gate row runs this same check on every column.

RUN=$(curl -s -X POST $API/runs -d '{
  "case_ids": ["sent-01","sent-02","sent-03",
               "sent-08","sent-13"],
  "candidates": [{"model_id": "llama3-2-3b"}],
  "methods": ["exact_match"] }' | jq -r .id)

# poll GET $API/runs/$RUN until "completed"
# accuracy = mean(exact_match values)

exact match accuracy: 0.80 over 5 cases
exit code: 1        # gate fails, release blocked

~5 min. That output is real: Llama 3.2 3B scored 0.80 on these five cases when this was tested, so the gate fails. If there's time, run it live. The full working script is in the Lab Companion page (it uses Python instead of jq and sets the content-type header).

Or show it in the app: run the Matrix with these five cases and Llama 3.2 3B, and the Gate row reads BLOCKED, exact_match 0.80 < 0.90, the same answer as the script. Lower the threshold live to show the verdict flip.

Wrap-up

What to take home

Criteria first

Decide what "better" means as a number before touching the prompt.

Fit the mechanism

Use the cheapest mechanism that fits the task: labels get exact match, code gets tests.

Check your judges

An LLM judge is a model too. Measure its agreement before trusting it.

Gate on it

The eval set is a spec. Run it on every change and block regressions.
