Before you start

Start the three services

Ollama starts on its own at login. The backend and the app each need a terminal. Ports 8000 and 5173 are taken by an SSH tunnel on this laptop, so the app uses 8001 and 5174, set in frontend/.env.

cd ~/openslava26-workshop-evaluations/backend

  workshop_evals.adapters.inbound.http.app:app \

cd ~/openslava26-workshop-evaluations/frontend
npm run dev
# serves http://localhost:5174
Check Ollama and the models 
ollama list

Deterministic evaluation

Tab: Playground

Turn "it seems fine" into a number with exact match on sentiment, then add a judge and watch the two verdicts disagree.

Prompt
From dataset · sentiment_classification · start at sent-01
Candidate
Qwen3 4B (local)
Mechanisms
Exact match then add LLM judge
Judge
Llama 3.2 3B (local)
Exact match is more lenient than the lab says

It passes if the reference appears anywhere in the response, so "I would classify this as positive." scores 1.0. Failures here mean the model chose the wrong label, or the response contains another label word. They don't mean the answer was wrapped in a sentence.

What to look for

  • On classification, exact match is binary. Averaged over cases it becomes accuracy.
  • The judge gives a continuous score. Ask what 0.6 would mean for a classifier, and how you would act on it.
Reflection
  • Would you trust 100% on 5 cases? On 50? How many cases do you need before you believe the number?
  • What does the cleaner exact-match number tell you about matching the mechanism to the shape of the task?

The self-judge warning is easy to miss
There is no warning banner. When candidate and judge are the same model, the judge's justification starts with "self-evaluation: judge equals candidate."

      
What to look for

      
    
        
  • For instruction following, completeness often drops before correctness does.
    • 
        
  • Rate the response yourself first. Where you and the judge disagree a lot, the judge or the weights are off for this task.

Judge reliability
Tabs: Judge reliability, Compare, Ensemble

        
Evaluate the evaluator. Measure how closely a judge agrees with a stronger reference judge, test it for position bias, and average several judges.

      

      

        
Dataset
writing (8 cases; every case is used)

        
Candidate
Qwen3 4B (local)

        
Judge under test
Llama 3.2 3B (local)

        
Reference judge
Qwen2.5 Coder 7B (local), the strongest judge available without cloud keys

        
Verdict rule
reliable: Pearson ≥ 0.7 and MAE ≤ 1.5 · questionable: Pearson ≥ 0.4 · otherwise unreliable

      

      
    
        
    • 
        
    • 
        
    • 
        
    • 
        
    • 
        
    • 
      

      
Different words in the app
The lab's middle verdict "uncertain" is shown as questionable. The lab also says the page warns about a self-judging setup; it doesn't, so watch which models you picked.

      
What to look for

      
    
        
  • A high MAE on correctness is serious. On clarity or efficiency it is less alarming, since those are more subjective.
    • 
        
  • If one judge squeezes all scores into a narrow band, Pearson drops while Spearman can stay high.
    • 
        
  • Both judges here are small local models. Treat "reliable" as "agrees with a slightly larger model", not as ground truth.
    • 
      

      
Reflection
    
        
  • If a judge is unreliable, what would you change first: the rubric, the model, or the task scope?
    • 
        
  • With only 8 cases, how much weight can you put on a Pearson r?
    • 
        
  • How would you bring human ratings into this loop?

An eval gate, end to end

      
This uses the same endpoints a CI job would: POST /api/runs, poll GET /api/runs/{id}, then compute accuracy and exit non-zero below 0.90. It was tested against this backend: Llama 3.2 3B scored 0.80 on these five cases, so the gate fails with exit code 1.

      
API=http://localhost:8001/api
RUN=$(curl -s -X POST $API/runs -H 'content-type: application/json' -d '{
  "case_ids": ["sent-01","sent-02","sent-03","sent-08","sent-13"],
  "candidates": [{"model_id": "llama3-2-3b", "label": "small"}],
  "methods": ["exact_match"]
}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')
until curl -s $API/runs/$RUN | grep -qE '"status":"(completed|failed)"'; do sleep 2; done
curl -s $API/runs/$RUN | python3 -c '
import json, sys
run = json.load(sys.stdin)
vals = [s["value"] for r in run["results"] for s in r["scores"] if s["method"] == "exact_match"]
acc = sum(vals) / len(vals)
print(f"exact match accuracy: {acc:.2f} over {len(vals)} cases")
sys.exit(0 if acc >= 0.90 else 1)'
echo "exit code: $?"

      
What to look for

      
    
        
  • The column to deploy is the cheapest one that clears your threshold, not necessarily the top scorer.
    • 
        
  • An error chip means a model call or parse failed. Open that case in the Playground to debug it.
    • 
      

      
Reflection
    
        
  • Which mechanism would you trust as a CI gate for classification? For code? For customer-facing writing?
    • 
        
  • Who owns the evaluation set, and who is allowed to change it?
    • 
        
  • What is the biggest obstacle to running this gate in your current project?
